# Development

## Requirements

- Rust through `rustup`. `rust-toolchain.toml` pins the toolchain with `clippy` and `rustfmt`;
  rustup installs it on first use.
- Git.
- `cargo-deny` 0.20.2: `cargo install cargo-deny --version 0.20.2 --locked`.
- On Windows, the MSVC build tools. On Linux, the packages the CI workflow installs
  (`.github/workflows/ci.yml`): the ALSA headers for cpal and the windowing libraries for eframe.
- Integration tests write their temporary files under `target/`, never elsewhere.

## The gate

```
cargo xtask ci
```

It runs these steps in order and stops at the first that fails. CI runs the same command.

| Step | What it checks |
| --- | --- |
| `cargo fmt --all -- --check` | Formatting |
| `cargo clippy --workspace --all-targets -- -D warnings` | The workspace lints: no `unsafe`, no `unwrap`, `expect`, `panic!`, `todo!`, `unimplemented!`, `unreachable!` or `dbg!` outside tests |
| `cargo test --workspace` | Unit, integration and documentation tests |
| `cargo xtask layers` | The layer rules of `docs/architecture.md`, the reach of the real-time module of the engine and the dependency registry |
| `cargo deny check` | Licences, security advisories, unmaintained and duplicated crates, sources (`deny.toml`) |
| `cargo xtask cleanroom` | No third-party material that must stay out |
| `cargo xtask parity --check` | `docs/parity.toml` is valid and `ROADMAP.md` matches it |

Each `xtask` step can be run alone. No test opens a real audio device: CI has no sound card.

### `cargo xtask cleanroom`

It reads every tracked file and fails on:

- the name of the reference product or of its vendor, in a path or in the text,
- a GPL, AGPL or LGPL licence header or SPDX tag,
- an audio file, by extension or by signature, whose path is not in `ATTRIBUTION.md`,
- a file with a mapping or collection extension of the reference product (`.tsi`, `.nml`)
  outside a `tests/fixtures/` directory.

### `cargo xtask privacy`

It is not part of the gate. It reads every file in the Git index, so staged files are covered before a commit, and the
author, committer and message of every commit. It fails on:

- an absolute user path: a drive followed by the users folder and a name, or a Unix home root
  followed by a name. Placeholders such as `/home/<name>` pass;
- the name of the current user, machine or domain as a whole word. The names are read from the
  environment when the check runs; the report names the variable, not the value;
- a Git identity generated by the system (`.local`, `.localdomain`, `(none)`);
- an image with metadata. PNG, JPEG and SVG are inspected; other image formats are rejected
  because the check cannot read them.

In CI (`CI=true`) the environment describes the runner, so the check of local names is skipped
there. The reasons are in `docs/decisions/0003-privacy-check-scope.md`.

### `cargo xtask parity`

`docs/parity.toml` is the feature inventory: areas, and in each area features with an
identifier, a name, a milestone (`M0` to `M5`, or `later`), a status (`planned`, `in_progress`,
`done`) and, when done, the test or command that demonstrates it.

`cargo xtask parity` validates the file and rewrites the progress table in `ROADMAP.md`.
`cargo xtask parity --check` validates and fails if the table is out of date.
`cargo xtask parity --site <folder>` writes the public progress page (`index.html`) and a badge
(`badge.svg`) into a folder; `.github/workflows/pages.yml` publishes them once the repository
is public.

## The command-line tool

```
cargo run -p platter-cli -- info <file>
cargo run -p platter-cli -- render --script <mix.toml> --out <mix.wav> [--log <file>]
```

`info` prints the format, duration, channels and sample rate of an audio file. `render` runs a
script through the engine without a sound card and writes the mix as a stereo WAV file with
32-bit float samples; the same script gives the same file on every run.

A script is a TOML file: `seconds` (length of the mix), an optional `sample_rate` (48000 by
default) and a list of `[[command]]` entries. Each entry has `at` (seconds from the start),
`id` (a command identifier from `crates/engine/src/command.rs`) and the parameters of that
command by name. Paths are relative to the script. `examples/two-deck-mix.toml` is a complete
example; it needs two audio files next to it, which the repository does not hold.

## The application

```
cargo run --release -p platter
cargo run -p platter -- --capture <state> <file.png>
cargo run -p platter-audio-io --example probe
```

The first opens the application. It keeps its settings, its shortcut file and its log in a
folder of its own inside the configuration folder of the user (`docs/behavior/settings.md`).

`--capture` draws one state of the interface from invented data, with no engine and no audio
device, at 1440 by 900 pixels, and saves it as a PNG. The states are `main`, `startup`,
`preferences-audio` and `preferences-general`, one per reference screen of M2 in
`docs/design/screens/`. Write the pictures to `target/screenshots/`, which is not tracked, and
compare them with the screens side by side.

`probe` opens the default audio device, plays half a second of silence and prints what the
stream runs at. It is the manual check of the device backend, which no test covers.

What no test can check, listening above all, is in `docs/maintainers/m2-manual-check.md`.

## Daily workflow

- Work on a branch. Changes reach `main` through pull requests: one per crate or logical unit,
  in dependency order, with a Conventional Commit title, the gate green, squash-merged. Push
  and open them when the maintainer asks.

- One commit per logical unit, Conventional Commits with the crate as scope, the milestone in
  the body. See `AGENTS.md` for the full rules.
- Before each commit: `git status --short`, `git diff --stat`, `git diff --check`. Add explicit
  paths.

## Adding a dependency

1. Check that it is on the approved list in `docs/dependencies.md`. If it is not, stop and ask
   the maintainer.
2. Add it with `cargo add`, move the version to `[workspace.dependencies]` and read the
   documentation of that exact version before using it.
3. Keep it confined to one crate or module, behind a project type or trait when the rest of the
   code would otherwise see its types.
4. Add its row to `docs/dependencies.md`. `cargo xtask layers` fails without it.
5. Run `cargo deny check`. A new permissive licence in the tree is added to `deny.toml` with a
   comment naming the crate that brings it; a copyleft licence means removing the dependency.
6. Justify it in the commit message: what for, licence, and why the project does not write it.

## Decision records

A technical decision the rules leave open is recorded in `docs/decisions/` as a short numbered
file: context, options, choice, how it was measured. A record is not edited after the fact; a
later record supersedes it.

## Behaviour notes

Before implementing a function of the inventory, write its note in `docs/behavior/<area>.md`:
what the public manual says it does, with the URL of the section; where Platter departs from it
and why; the edge cases. The tests of the function refer to the note.
