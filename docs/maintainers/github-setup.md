# GitHub setup

Settings of the repository on GitHub. They are applied by the maintainer by hand; nothing in this
repository applies them. The repository lives in the personal account of the maintainer, on the
free plan, and is private until the maintainer decides to make it public.

## While the repository is private (free plan)

- **Visibility:** private.
- **Pull requests:** Settings > General > Features > Pull requests: creation limited to
  "Collaborators only" from the start, so it is already in place on the day the repository
  becomes public (`docs/decisions/0001-pull-requests-limited-to-collaborators.md`).
- **Merging:** squash merging only; automatically delete head branches.
- **Actions:** default workflow permissions read-only. Minutes are limited on the free plan and
  macOS runners consume ten times more, so `ci.yml` runs Linux and Windows on each push and pull
  request and adds macOS only on the weekly schedule and on manual runs. The condition reads
  `github.event.repository.private`, so nothing has to change when the repository becomes
  public.
- **Security:** Dependabot alerts and Dependabot security updates.
- **CodeRabbit:** application installed. On private repositories its free plan only summarises
  pull requests.
- **Rule of `main`:** followed by convention (every change through a pull request). The free plan
  does not enforce branch rules on private repositories.

## Making the repository public

In this order, on the day:

1. Run `cargo xtask privacy` on a full clone. Making the repository public exposes the whole
   history.
2. Change the visibility to public.
3. Rule of `main`: changes through pull requests only; the `gate` checks of the three systems
   required; no force pushes; linear history; 0 approvals while there is a single maintainer.
4. Security: secret scanning with push protection, and private vulnerability reporting.
5. Actions: require approval for workflows from first-time contributors.
6. Discussions, with categories for questions, ideas and controllers.
7. GitHub Pages with the progress page generated by `cargo xtask parity --site` (the page and
   its workflow arrive in M1).
8. Check that the creation of pull requests is still "Collaborators only".

## Opening to external pull requests

In this order, when the maintainer decides to open:

1. The repository is already public. Check that `ci.yml` and `pr-quality.yml` are green on
   `main` and that the pinned commit of the anti-slop action is current.
2. Settings > Moderation options > Interaction limits > Pull request limits: enable the limit of
   open pull requests per user without write access (value to be decided when opening;
   <https://github.blog/changelog/2026-06-17-limit-open-pull-requests-for-users-without-write-access/>)
   and, if needed, the exempt list.
3. Settings > General > Features > Pull requests: change "Collaborators only" to everyone.
4. Remove the `external-prs-notice` block from `CONTRIBUTING.md` in a pull request of its own.
5. Review the rule of `main`: with more than one maintainer, require at least one approval.
6. Mark `docs/decisions/0001-pull-requests-limited-to-collaborators.md` as superseded by a new
   record that registers the opening.

## Files in this repository that GitHub reads

| File | Purpose |
| --- | --- |
| `.github/workflows/ci.yml` | The gate, `cargo xtask ci`, on each system |
| `.github/workflows/pr-quality.yml` | Quality filter for pull requests from outside the project |
| `.github/dependabot.yml` | Weekly updates of cargo dependencies and of the pinned actions |
| `.github/pull_request_template.md` | Checklist of a pull request |
| `.github/ISSUE_TEMPLATE/` | Forms for bugs, features and controller reports |
| `.coderabbit.yaml` | Automatic review, skipping Dependabot |

Actions are pinned by commit SHA with the version in a comment. A SHA is obtained with
`git ls-remote --tags https://github.com/<owner>/<repo>` and never written from memory;
Dependabot keeps them current.
